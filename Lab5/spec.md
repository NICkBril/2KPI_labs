# Специфікація діаграми компонентів

## Архітектура iCARus


### Мета

Показати систему iCARus загалом: з яких частин вона складається, які в них інтерфейси й залежності та де проходить межа системи. Діаграма не описує окремий процес, а збирає в одне ціле попередні лабораторні: дані (Lab 1), вимоги та UC (Lab 2), взаємодію (Lab 3) і процес оплати (Lab 4). Нових вимог не додаємо.


### Вибір структури

Обрано **варіант A: горизонтальні шари**. У Lab 3 сервіси вже працюють з репозиторіями по шарах, а ER-модель одна й має зв'язки між сутностями (`Rental` посилається на `Customer` і `Car`, `Payment` на `Rental`), тому ділити її на окремі схеми по модулях незручно.

### Межа системи

- **Всередині:** iCARus UI, iCARus Backend, iCARus DB.
- **Зовні:** Payment Gateway (зовнішній сервіс з Lab 2). Браузер користувача окремим компонентом не показано.

### Інтерфейси та порти

| Інтерфейс | Надає | Потребує | Порт Backend |
|---|---|---|---|
| REST API (каталог, деталі, доступність, реєстрація, створення, скасування й перегляд оренд, початок оплати) | API Router | iCARus UI | HTTP in |
| Payment Callback (результат платежу, UC-07) | API Router | Payment Gateway | webhook in |
| Payments API (платіжний запит) | Payment Gateway | PaymentGatewayClient | PSP out |
| SQL Access | iCARus DB | CarRepository, CustomerRepository, RentalRepository, PaymentRepository | SQL out |

- Зв'язок з БД іде через порт SQL out, репозиторії ходять у БД лише так.
- Весь зовнішній трафік (UI і платіжна система) іде через HTTPS (NFR-7, NFR-12).
- Callback обробляє повторні підтвердження відповідно до NFR-13. Відповідь платіжній системі надсилається не довше ніж за 5 секунд, а повторні надсилання одного підтвердження приймаються протягом 24 годин після першої спроби (NFR-14).
- Усередині бекенду використано пряму залежність (пунктир), бо заміну внутрішніх компонентів не плануємо.

### Правила залежностей

- Напрямок: API → Service → Data Access → DB.   PaymentService → PaymentGatewayClient → Payment Gateway
- Сервіси можуть залежати від інших сервісів, як у Lab 3: RentalService → AuthService, AvailabilityService, PricingService; PaymentService → RentalService, AuthService; DeadlineScheduler → PaymentService. Циклів немає.
- Автоскасування: DeadlineScheduler викликає PaymentService, той перевіряє UB-6 і просить RentalService змінити статус оренди.
- У БД ходять лише репозиторії.

### Не включено

- **Email, SMS, push.** US-3 каже лише "показати підтвердження", спосіб Lab 4 не визначає (припущення 5).
- **OAuth / Identity.** Механізм входу поза обсягом Lab 2.
- **Черга й кеш.** У Lab 2–4 немає асинхронної обробки, callback обробляється одразу (NFR-14).
- **Адмін-панель.** Роль адміністратора не розглядається (NFR-1).
- **Окремі контролери.** Router передає запити сервісам напряму.
- **Введення даних картки.** Де його роблять, не визначено, система їх не зберігає (NFR-9).

### Критерії узгодженості

- Кожен компонент має обгрунтування в Lab 1–4.
- Усі учасники діаграм Lab 3 є на діаграмі.
- Кожна сутність ER має репозиторій: `Car` і `CarModel` разом у CarRepository (як у Lab 3), `Customer`, `Rental`, `Payment` окремо.
- Кроки процесу з Lab 4 мають компонент: створення `Payment`, платіжний запит, callback, повтори, таймер.
- Межа системи відокремлює власні компоненти від Payment Gateway, кожен зовнішній зв'язок іде через інтерфейс і порт.
